DIGIT Security Posture

What this is

A standing measurement of how safely our Kubernetes environments are configured. Two tools produce it: Kubescape, which reads every workload and checks it against the CIS Kubernetes Benchmark, and Kyverno, which watches what gets deployed and records anything that breaks the Pod Security rules.

Both run on a schedule and change nothing. Nothing here blocks a deployment.

What the score means

The headline percentage is the CIS Kubernetes Benchmark, an industry standard, measured over the part of it we control: how our own workloads are set up. 100% would mean every workload satisfies every check.

It is not a measure of whether we have been attacked, and not a count of vulnerabilities. Those are separate, and both are on this page.

What it is not

Roughly two thirds of the CIS benchmark examines the machines that run Kubernetes itself. Our clusters are managed by the cloud provider, who does not expose those machines, so we cannot check them and we do not score them. The provider certifies that layer separately.

We report what we measured, and say plainly what we did not.

How to read it

Every number here can be opened. Click any figure with a dotted underline to see what it counts, the arithmetic behind it, and the exact services affected.

Movement matters more than the absolute value. A number against a published standard, trending the right way, is the thing to watch.

What to fix — configuration

Kubescape checks that are failing, most-affected first, each with the services it lands on. Check names and remediation are upstream Kubescape’s own text, not ours. A count is failing findings, so one service can appear under several checks.

Kyverno policies

Image vulnerabilities

Known vulnerabilities in the software inside our container images, found by scanning each image. These are overwhelmingly inherited from the public base images we build on rather than written here, which is why they sit beside the compliance score instead of inside it — they move with upstream disclosures rather than with our work. The route to reducing them is rebuilding on newer or slimmer base images.

Audit, not enforcement. Kyverno reports violations and admits the resource anyway. Its webhooks are also fail-open, so if Kyverno is unavailable the API server proceeds rather than blocking deployments.

The score is computed here, and so is its history. Nothing in the cluster stores either. Kubescape’s operator writes findings; the score its CLI shows is calculated by the client, so the collector reimplements the upstream formula — a check that passes scores 100, otherwise passed/all, and the section score is the plain mean across checks, unweighted by severity. That plain mean is why a movement can be attributed exactly: each check carries 1/N of the score, so the per-check changes sum to the total. Because the storage API overwrites every summary in place on each scan, history exists only because each run appends a point to a ConfigMap.

Scored over what we can see. The CIS figure covers the workloads this scan-only profile collects, so it will not match kubescape scan run from a laptop, which also evaluates host- and cluster-level checks this deployment does not gather. It is consistent with itself, which is what a trend needs.

Platform namespaces are counted separately. kube-system components legitimately need hostPath, hostNetwork and privileged mode, so their policy violations are not mixed in with work anyone is going to do.

Collection. Kyverno PolicyReports are ordinary cluster resources and list cleanly. Kubescape summaries come from an aggregated API whose LIST returns every figure as zero — only a GET of each object carries real numbers, so the collector fetches them one at a time.
